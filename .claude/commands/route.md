다음 작업을 아래 기준으로 분류하고, 가장 맞는 서브에이전트 하나에 Agent 도구로 맡기세요.
작업: $ARGUMENTS

## 분류 순서 (위에서부터 물어보고, 처음 "예"인 것으로 정한다)

### ① 간단한 작업이면 Haiku (`haiku-worker`) — 가장 먼저 확인
아래 중 하나라도 해당하고 다른 항목에 해당하지 않으면 Haiku다.
- 파일 1~2개, 한 곳만 보면 되는 조회 ("이 함수는 어디서 쓰여?", "이 값은 어디 정의돼 있어?")
- 한 줄~몇 줄 수정이고 정답이 정해져 있음 (오타, 이름 바꾸기, import 정리, 문구 수정)
- 로그·출력·목록을 요약하거나 표로 바꾸기
- 설명 요청 중 코드 한 곳만 확인하면 되는 것

### ② 최고 난이도면 Fable (`fable-expert`)
- 이미 Opus로 시도해 실패함, 또는 여러 설계 결정이 얽힌 어려운 버그
- 출시 전 전체 점검

### ③ 판단·설계면 Opus (`opus-architect`)
- 여러 패키지(엔진·게임·홈)에 걸친 변경, 구조 설계, 리팩토링 계획
- 공통 컴포넌트 신설, 원인이 여러 갈래인 버그, 설계 대안 비교

### ④ 그 밖의 일상 개발이면 Sonnet (`sonnet-worker`)
- 기능 추가, 버그 수정(원인이 명확할 때), 테스트 작성
- 한 게임 안의 규칙·UI 변경, 문서와 계획 파일 갱신
- ①에 해당하지만 여러 파일을 깊게 고쳐야 하면 Sonnet이다.

**주의**: "애매하다"는 이유로 Sonnet을 고르지 않습니다. ①의 조건을 하나씩 확인하고, 해당하면 Haiku를 고릅니다. 간단한 일을 비싼 모델에 맡기는 것이 가장 큰 낭비입니다.

## 실행 방법

1. 작업이 비어 있으면 무엇을 할지 한 번만 물어봅니다.
2. 분류 결과를 **한 줄**로 알려줍니다. 예: "→ 여러 패키지 설계이므로 opus-architect(Opus)에 맡깁니다."
3. Agent 도구로 해당 서브에이전트를 호출하고, 작업 내용과 배경(관련 파일, 이미 시도한 것)을 충분히 넘깁니다.
4. 서브에이전트의 결과를 받아 사용자에게 요약합니다.
5. 서브에이전트가 "중단"하거나 원인을 못 찾았다고 보고하면, 한 단계 위 모델로 **한 번만** 다시 맡깁니다(haiku → sonnet → opus → fable). 그 이상 올리기 전에는 사용자에게 확인합니다.

## 공통 규칙

- 서브에이전트는 커밋과 push를 하지 않습니다. 커밋은 사용자가 따로 요청할 때만 합니다.
- 결과는 `pnpm check` 통과 여부와 함께 보고합니다.
